🤔 Pregunta esencial

¿Qué necesitas saber para decidir si un cambio puede avanzar? El caso de Knight Capital muestra que una decisión segura combina pruebas, revisión, controles de despliegue y límites operativos; una sola prueba no garantiza por sí misma que no habrá fallas.

Ruta de inicio · 20 min

Antes de automatizar: aprende a decidir qué probar

La guía sigue una secuencia: primero entiendes el problema, luego practicas con un caso pequeño y al final transfieres la decisión a tu propio proyecto. El framework llega después de la pregunta, no antes.

  1. Define una regla observable.Escribe qué entrada recibe tu función o pantalla y qué resultado correcto esperas.
  2. Elige casos representativos.Incluye un caso válido, uno inválido y los valores que están justo en el límite.
  3. Ejecuta primero un caso manual.Registra entrada, pasos, resultado esperado, resultado observado y si hubo un defecto.
  4. Automatiza el mismo comportamiento.Usa preparar–actuar–comprobar; una prueba verde sin una aserción útil no demuestra nada.
  5. Transfiere la técnica.Cambia el ejemplo por una regla de tu aplicación y explica qué conservarías y qué adaptarías.

Orden recomendado para comprender y practicar

Fundamentos → Diseño y niveles → TDD → BDD → una tecnología (FastAPI, Flask, React o Java) → E2E → Cobertura → CI/CD → Reto y evidencias. Observabilidad e IA son ampliaciones. Los módulos se pueden consultar por separado; las cuatro tecnologías son alternativas.

En TDD y BDD usarás el mismo laboratorio de préstamos. Primero explica la regla, luego ejecútala y finalmente registra lo que demostraste. Conserva ART-TEST-01 como plan, ART-TEST-02 como suite y ART-TEST-03 como recorridos y defectos.

Qué puede demostrar esta guía

La guía ayuda a diseñar, ejecutar y documentar pruebas en un entorno de práctica. No certifica que una aplicación esté libre de defectos, segura o aprobada; esas decisiones requieren alcance, datos, versiones y revisión humana explícitos.

Cómo trabajarás con IA sin perder el criterio

En cada módulo encontrarás una práctica opcional con la misma secuencia. La IA acelera el borrador; tú entiendes la regla, compruebas el resultado y respondes por la decisión.

  1. 1ComprenderExplica la regla y el riesgo con tus palabras.
  2. 2EncargarEntrega contexto mínimo y pide una salida verificable.
  3. 3CuestionarBusca supuestos, omisiones y nombres inventados.
  4. 4ComprobarEjecuta la prueba o contrasta con fuentes reales.
  5. 5DecidirAcepta, corrige o rechaza y registra por qué.

🛠️ Cómo se construyen las pruebas durante el desarrollo (Shift-Left)

No esperamos a que la aplicación esté terminada para probar. El orden lógico al programar va de los requisitos a los flujos:

  1. Diseño de casos (BVA): Particiones válidas, inválidas y fronteras críticas antes de codificar.
  2. TDD Unitario: Escribir el test que falla (Rojo) antes del código de producción (Verde).
  3. Aislamiento (Dobles de prueba): Sustituir bases de datos y APIs lentas con Mocks/Stubs.
  4. Recorrido E2E: Validar la experiencia integral de usuario en el navegador real.

1.1 Diseño de Casos: Partición de Equivalencia & Valores Límite (BVA)

Reduce casos repetidos sin perder señales importantes. Determina particiones y fronteras (n-1, n, n+1) donde un cambio de regla puede revelar defectos.

1.2 TDD Interactivo: Ciclo Rojo - Verde - Refactor

Experimenta el ciclo de diseño guiado por pruebas: activa la aserción que falla, crea la implementación mínima y limpia el código manteniendo verde el semáforo.

1.3 Aislamiento con Dobles de Prueba (Mocks, Stubs, Spies, Fakes)

Identifica cuándo usar un Stub para datos estáticos, un Mock para verificar llamadas externas o un Fake en memoria para no saturar servidores reales.

1.4 Recorrido E2E: del objetivo a la evidencia

Elige un escenario y observa cómo una prueba de extremo a extremo pasa por navegador, localizador, acción, sistema y aserción con Playwright.

⚡ Cómo se ejecutan las pruebas en integración continua (Fast-Feedback Pyramid)

En el servidor CI/CD, el orden es inverso al costo y duración: lo más rápido corre primero para alertar al equipo en segundos (Fail Fast):

  1. Linter / Sintaxis (< 2s): Errores tipográficos y formato.
  2. Pruebas unitarias: Lógica aislada y retroalimentación rápida.
  3. Pruebas de integración y contrato: Comunicación entre componentes y datos controlados.
  4. Recorridos E2E críticos: Objetivos completos en navegadores reales.
  5. Compuerta de calidad: Criterios acordados según riesgo, resultados y evidencia.

Ubica cada tipo en la capa que suele ofrecer retroalimentación más rápida. La forma orienta la estrategia; la mezcla concreta depende del riesgo y la arquitectura.

02A

Si algo falla

Diagnostica antes de cambiar el código

Sigue siempre el mismo orden: ubicación, versión, entorno activo, dependencia y después la prueba. Así separas un problema de preparación de un defecto del aplicativo.

1. ¿Estás en la carpeta correcta?

La carpeta debe contener requirements.txt y tests/. Si no aparecen, vuelve a la carpeta que extrajiste.

Get-Location
Test-Path requirements.txt
Test-Path tests

2. ¿Usas el Python del proyecto?

Activa el entorno y comprueba la ruta que ejecutará la suite. Si la ruta no termina en .venv, activa de nuevo.

.\.venv\Scripts\Activate.ps1
python --version
python -c "import sys; print(sys.executable)"

3. Falta una dependencia

Instala desde el archivo del proyecto y ejecuta PyTest a través del mismo intérprete.

python -m pip install -r requirements.txt
python -m pytest tests/unit/ -q

4. La prueba falla de verdad

Conserva el comando, caso, esperado, observado y versión. Un error 422 suele indicar datos de entrada inválidos; revisa response.json()['detail'] antes de corregir.

python -m pytest tests/ -v
python -m pytest tests/ --tb=short

Regla de decisión

Si falla la preparación, corrige el entorno y repite la misma prueba. Si el entorno está correcto y el resultado contradice el oráculo, registra un defecto; no lo ocultes desactivando la aserción.
